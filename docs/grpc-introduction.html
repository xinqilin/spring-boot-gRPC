gRPC 圖解入門

gRPC 讓一支程式直接呼叫另一台機器上的方法，寫起來就像呼叫自己的函式。這一頁每張圖只講一件事，用的都是這個 repo 裡真的在跑的程式碼和測試結果。

  • client 送出的訊息
  • server 回覆的訊息
  • 錯誤

契約

.proto 是雙方先講好的合約

有哪些方法、每個訊息長什麼樣子，都寫在 .proto 檔裡。兩邊照同一份合約產生程式碼。

打包

protobuf 只送編號和值

欄位名稱不會送出去，每個欄位靠 .proto 裡的編號辨認，所以訊息比 JSON 小很多。

傳輸

HTTP/2：一條連線同時跑好幾個呼叫

gRPC 跑在 HTTP/2 上。每個 RPC 是一條 stream，很多條 stream 共用同一條 TCP 連線。

四種呼叫方式

差別只在 stream 放在哪一邊

.proto 裡的 stream 關鍵字放在請求、回應、兩邊或都不放，就是四種模式。

Unary一問一答

rpc SayHello(HelloRequest)
    returns (HelloReply)

呼叫一次、回一次，用起來像一般的 REST API。

Server-streaming訂閱

rpc Subscribe(HelloRequest)
    returns (stream HelloReply)

送一次，server 陸續推好幾筆回來，像訂閱通知。

Client-streaming上傳彙總

rpc Upload(stream HelloRequest)
    returns (UploadSummary)

client 陸續送很多筆，server 收完才回一筆彙總。

Bidirectional雙向

rpc Chat(stream HelloRequest)
    returns (stream HelloReply)

兩邊各自送、各自收。這裡的實作是收到一筆就回一筆。

server 內部

呼叫進來，要先穿過 interceptor

請求由外往內經過每一層 interceptor 才到你的程式，回覆或錯誤再由內往外穿出來。順序會影響每一層看得到什麼。

出錯時

錯誤要轉成標準的狀態碼

gRPC 用一組固定的狀態碼表示錯誤。client 看代碼就知道要修正參數、重試，還是放棄。

  • OK成功
  • INVALID_ARGUMENT參數不合法
  • NOT_FOUND找不到
  • DEADLINE_EXCEEDED超過時限
  • CANCELLED被取消
  • UNAVAILABLE暫時連不上
  • UNKNOWN不明錯誤

紅框是這個 repo 有示範的狀態碼。client-streaming 的 Upload 示範另一種寫法：在 onNext 裡直接呼叫 responseObserver.onError(Status.INVALID_ARGUMENT…)。

時間限制

Deadline：client 只等 300ms

client 可以替每次呼叫設時限。時間一到，client 收到 DEADLINE_EXCEEDED，server 也會知道對方不等了。

流量控制

Flow control：client 讀多快，server 就送多快

server 一直送、client 來不及讀，訊息就會堆在 server 的記憶體裡。用 isReady() 和 onReadyHandler，可以等 client 有空再送。

動手試試

自己跑跑看

需要 JDK 21。手動呼叫要先裝 grpcurl（macOS：brew install grpcurl）。

# 啟動 server（port 9090）
./gradlew bootRun

# 另開一個 terminal：列出服務、呼叫 SayHello
grpcurl -plaintext localhost:9090 list
grpcurl -plaintext -d '{"name": "Bill"}' \
  localhost:9090 streaming.unary.UnaryGreeter/SayHello

# 跑全部測試（不用先啟動 server）
./gradlew test
